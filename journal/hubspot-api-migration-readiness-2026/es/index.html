PANORAMA TÉCNICO · 2026

Hay automatizaciones que nadie nota mientras funcionan. Un formulario manda un contacto al CRM, una oportunidad cambia de etapa o un sistema actualiza información sin que alguien tenga que copiarla. El problema aparece cuando la plataforma cambia una API y nadie recuerda quién construyó la integración.

HubSpot anunció modificaciones a APIs antiguas, funciones serverless y entornos de ejecución para código personalizado. No significan que todas las cuentas vayan a fallar. Algunas medidas impiden editar funciones existentes; otras marcan cuándo determinados endpoints dejan de responder.

Las fechas importantes

  1. 0117 novLímite para editarFunciones antiguas y acciones de workflow en Node.js 20
  2. 024 dicRetiro definitivo de APIDejan de funcionar las llamadas a Pipelines API V1
  3. 031 feb 2027Fin de serverless antiguoDejan de responder las funciones de Design Manager

Fuente: anuncios oficiales de HubSpot; no se presume impacto en cada empresa.

Para Pipelines API V1, HubSpot indica migrar a una versión con fecha 2026-03 o posterior, y recomienda 2026-09. Para funciones serverless antiguas, el camino es reconstruirlas en proyectos de desarrollo. Las nuevas rutas usan /hs/serverless/. En acciones personalizadas, pasar a Node.js 24 también puede requerir adaptar bibliotecas y controladores.

¿Tu empresa está afectada?

No se puede saber sólo porque utilice HubSpot.

Que una empresa use el CRM no significa que dependa de esas APIs. Que aparezca Node.js 20 en un archivo no demuestra que se esté ejecutando en producción. Y que nadie encuentre un endpoint antiguo en el repositorio interno tampoco descarta una integración creada por un proveedor externo.

Antes de contratar una migración, conviene responder siete preguntas:

  1. ¿Qué sistemas se conectan hoy con HubSpot?
  2. ¿Quién es responsable de cada integración y quién puede aprobar cambios?
  3. ¿Existe evidencia de llamadas recientes a Pipelines API V1?
  4. ¿El sitio usa funciones del antiguo Design Manager o rutas /_hcms/api/?
  5. ¿Qué acciones de código personalizado tienen los workflows y en qué versión de Node se ejecutan?
  6. ¿Dónde se puede probar un cambio sin tocar la operación real?
  7. ¿Cómo se revierte una migración y quién valida que el proceso siga funcionando?

Qué debe entregar una revisión útil

Una lista de integraciones activas y sus responsables; evidencia de cuáles utilizan tecnología afectada; la fecha y fuente oficial aplicable; el proceso de negocio involucrado; y un plan de pruebas y reversión cuando haga falta intervenir.

Si no hay evidencia suficiente, la conclusión correcta es por confirmar. No hace falta convertir cada anuncio de un proveedor en una emergencia ni entregar contraseñas o acceso irrestricto para iniciar una conversación.

Cómo puede ayudarte Sovtiva

En Sovtiva trabajamos con procesos que conectan sitios web, CRMs, hojas de cálculo y automatizaciones. Cuando existe una duda real sobre HubSpot, primero buscamos entender qué está funcionando, qué depende de código antiguo y qué fecha aplica. Después se puede definir una revisión técnica y, cuando esté justificado, un proyecto de migración con alcance y autorización separados.

El primer paso no es comprar una herramienta nueva. Es identificar qué parte del trabajo dejaría de funcionar si una integración antigua fallara.
