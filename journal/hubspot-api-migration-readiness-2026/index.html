Your HubSpot account isn’t expiring.
Some older integrations might be.

Three deadlines worth checking before December, and a way to find out whether they actually affect your business.

Sovtiva Research DeskNovember 13, 2026Technical field guide · EN/ES

TECHNICAL FIELD GUIDE · 2026

An integration usually becomes important when nobody has to think about it. A deal moves to the next stage, a workflow updates a property, a website form passes information to a CRM. Then a platform changes an API, and the team has to answer a question it hoped it wouldn't face: who built this, and what still depends on it?

HubSpot has announced a series of changes to older APIs, serverless functions and custom-code runtimes. They don't affect every account in the same way. Some are restrictions on editing old code. Others are dates when specific endpoints stop working. That distinction matters more than the headline.

For Pipelines API V1, HubSpot points developers toward the date-versioned 2026-03 API or newer, recommending 2026-09. For legacy design-manager functions, HubSpot recommends rebuilding in developer projects, where serverless routes use /hs/serverless/ instead. Node.js 24 custom-code actions may require changes to handlers and libraries, not just a version switch.

Does this affect your company?

Not necessarily. A team using the standard HubSpot CRM interface isn't automatically using a legacy API. A Node.js 20 reference in an old repository doesn't prove the code is active. Conversely, a clean search of your company's own code does not rule out integrations maintained by an agency or another SaaS provider.

Start with seven questions:

  1. What integrations connect HubSpot to your website, checkout, marketing or back-office tools?
  2. Who owns the code, vendor relationship and production change permission?
  3. Does anything still call Pipelines API V1? Can the technical owner show a recent call or configuration?
  4. Do your pages call /_hcms/api/ or depend on design-manager serverless functions?
  5. Which workflows use custom-code actions, and which Node runtime do those actions use?
  6. Is there a staging environment where you can test the replacement before changing production?
  7. If a change fails, what is the rollback plan, and who will confirm that the business workflow still works?

These answers are more useful than an automated warning saying every company using HubSpot is "at risk."

What a real readiness review should deliver

A useful review is a concise inventory of confirmed active integrations, their owners, the official rule that applies to each one, the business process involved, and the evidence of actual usage. Where a migration is needed, it should include a test plan and a rollback. Where there isn't enough evidence, the answer should be unknown, not a manufactured risk.

The workflow should be simple: first identify, then verify, then plan. Production changes come later, with a separate approval. There is no reason to hand over unrestricted HubSpot access or API tokens just to have an initial conversation.
